I come to language models from RL, so I tend to think about a coding assistant
as a policy. It reads a test failure, chooses a command, sees the result, and
tries a patch. Some of the tokens in its context are decisions it made. Others
came from the user or the terminal.

I've been working on **behavioral language modeling**, starting from the idea
that pretraining on these interactions is imitation learning. That led me to
compare learning the assistant's behavior with predicting the whole transcript.
I have some early results from that comparison below.

The policy view has also changed how I think about distillation and context
compression. A teacher might know something the student has never seen. A summary
might discard something the student will need later. In either case, predicting
the teacher's next token can be a poor guide to what the student should do.

## Actions and observations

Suppose a coding assistant is trying to fix a failing test.

The assistant chooses the command and receives the test output. Its patch
depends on both. We can write its policy as

$$
h_t=(o_0,a_0,o_1,\ldots,a_{t-1},o_t),
\qquad a_t\sim\pi_\theta(\cdot\mid h_t).
$$

Here $$a_t$$ is one generated token, and $$t$$ counts the agent's token decisions.
The observation $$o_t$$ contains any input received since its previous token.
While the agent is generating a response, no new input may arrive, so $$o_t$$ can
be empty. After a tool call, it can contain the tool's reply. The history $$h_t$$
includes all earlier observations and generated tokens. Instructions and observed
rewards can be included in the observations too.

The assistant has not read every file or found the cause of the failure yet. It
has to act with incomplete information. This is the setting of a partially
observable Markov decision process, or POMDP
{% cite kaelbling1998planning --file references %}.

The role follows who generated the token. Source code read from a file is an
observation. The same code in a patch is a sequence of actions. Quoting an error
message is also an action, since the assistant chose to emit it.

This depends on whose policy we are training. A model acting as a tool simulator
would generate the tool replies instead.

For a single uninterrupted completion, the usual token MDP works well. The state
is the prefix, the action is the next token, and the next state appends it. An
MDP can also account for incoming tool results through its transitions. I use the
POMDP view because I also want to think about what the agent has not seen and
what it needs to remember.

## A language model is a recurrent policy

The history in $$\pi_\theta(a_t\mid h_t)$$ has to reach the network somehow. A
recurrent policy maintains a memory of it

$$
z_t=f_\theta(z_{t-1},a_{t-1},o_t),
\qquad a_t\sim\pi_\theta(\cdot\mid z_t).
$$

The memory $$z_t$$ carries information from earlier steps. In a GRU, it is a hidden
state. A transformer can use a KV cache or recompute over its retained context.
External notes and retrieved records can provide memory too.

For example, a Wordle agent generates a guess and receives feedback about its
letters. Its next guess should use the feedback from all previous turns. A
recurrent RL algorithm can train this policy whether a GRU or a language model
processes the history.

A cache does not guarantee good memory. The model might fail to use information
that is present, and truncation might remove information it needs later. Nor is
a hidden state automatically a sufficient belief state. That would require it
to preserve all the information needed to predict the hidden state of the task.

Choosing a cache, summary, or retrieval scheme changes what the policy can
remember. HELM uses this connection directly, with a pretrained language model
compressing history for an RL agent {% cite paischer2022helm --file references %}.

## Pretraining is imitation

An autoregressive language model learns to predict the next token in a corpus

$$
\mathcal L_{\mathrm{CLM}}
=-\mathbb E_{x\sim\mathcal D}\sum_t
\log p_\theta(x_t\mid x_{<t}).
$$

Here $$t$$ counts positions in the corpus text. If the prefix is the history and
the next token is an action, this is behavioral
cloning with a log loss. The model learns to continue text like the text in its
training data {% cite foster2024bc --file references %}.

The authors in that corpus have different goals and levels of skill. An edited
document also hides most of the decisions its author made while writing it, so
the connection to imitation is clearest with recorded agent interactions.

For recorded agent interactions, we can identify the assistant's generated tokens
and train their likelihood given the preceding history

$$
\mathcal L_{\mathrm{BC}}
=-\mathbb E_{\tau\sim\mathcal D}\sum_t
\log\pi_\theta(a_t\mid h_t).
$$

Here $$t$$ counts generated tokens. The model predicts a command from the request,
then predicts a patch from the history that now includes the test result.
Generated reasoning, stop tokens, and tool-handoff tokens are actions too. Fixed
headers added by the interface are context.

The test output can train the model through its use in predicting the patch,
without being a prediction target itself. How far those gradients flow depends
on which computations are frozen, cached, or detached in the implementation.

## Learning to predict observations

Suppose we instead predict every next token in the recorded interaction. We now
train on the request and tool output as well as the command and patch. The summed
loss over the same target positions splits into two parts

$$
\mathcal L_{\mathrm{CLM}}
=\mathcal L_{\mathrm{BC}}+\mathcal L_{\mathrm{WM}}.
$$

Here $$\mathcal L_{\mathrm{BC}}$$ predicts the agent's actions and
$$\mathcal L_{\mathrm{WM}}$$ predicts observations given the preceding history.
I call the second term the world-model loss.

Predicting a test result might teach the model how the program works. It also
asks the model to predict details it may never need when choosing a patch. I
wanted to find out whether that extra training helps.

We can choose its weight explicitly

$$
\mathcal L=\mathcal L_{\mathrm{BC}}+\lambda\mathcal L_{\mathrm{WM}}.
$$

The loss normalization matters as well. If we average over all tokens, a long tool
output contributes more targets than a short command. Averaging each part
separately gives a different weighting.

This world-model loss fits observations in the dataset. Using it to predict what
would happen after an unrecorded action requires assumptions about how the data
was collected.

### What happened on AgentTrove

I ran this comparison on recorded AgentTrove interactions with randomly
initialized Qwen3-style models of about 82M, 191M, and 504M parameters. Within each
pair, the architecture, initialization seed, data order, and optimizer were held
fixed. CLM predicts all valid next tokens. BLM predicts only the assistant's
outputs. Both models read the observations. Each loss is averaged over the tokens
it scores.

I evaluated both models on the same held-out assistant tokens. The plots show
their average negative log probability, or action NLL, so lower is better. The
first plot uses an estimated FLOP budget for the horizontal axis.

better task performance or better learning during RL.

## Learning from reward

In RL, we evaluate the policy by what happens when it acts

$$
J(\theta)=\mathbb E_{\tau\sim P^{\pi_\theta}}
\left[\sum_t\gamma^t r_t\right].
$$

For the coding assistant, reward might depend on whether its patch passes the
tests. Imitation increases the likelihood of demonstrated actions. A policy
gradient update uses returns or advantages to change the likelihood of actions
taken during rollouts.

Both methods train $$\pi_\theta(a_t\mid h_t)$$. BC fits the demonstrator's choices.
RL changes the policy according to the rewards its choices earn.

The same reasoning applies to policy ratios. For two policies with the same
observation interface in a fixed environment, the environment terms cancel

$$
\frac{P^{\pi_\theta}(\tau)}{P^{\pi_{\mathrm{old}}}(\tau)}
=\prod_t
\frac{\pi_\theta(a_t\mid h_t)}{\pi_{\mathrm{old}}(a_t\mid h_t)}.
$$

This holds where the denominator is positive. Only action probabilities remain.
A KL penalty between policies also compares their choices. Adding a loss on the
model's predictions of tool outputs would be a separate objective.

As in BC, observations affect the update through the policy's use of them as
inputs.

With one token per step, discounting also happens per token unless we choose
otherwise. That can make a longer response worth less even if it reaches the
same result. The reward timing and discount should match the task we want to train.

## Learning on the student's histories

Once the coding assistant makes its own decisions, it may open different files,
write a different patch, or get a test failure absent from its demonstrations.
The history reaching the policy has changed. DAgger addresses this by asking an
expert for supervision on histories the learner visits {% cite ross2011dagger --file references %}.

In on-policy distillation, the student generates text and the teacher supplies
targets on those prefixes. Generalized Knowledge Distillation uses
student-generated sequences this way {% cite agarwal2024gkd --file references %}.
The objective is still imitation, now on histories the student actually visits.

This can teach the student how to recover from its own mistakes. But the teacher
may still give advice based on evidence the student has never seen.

### When the student should look first

Suppose the teacher has already seen the relevant source file. It can write a
patch immediately. The student has only seen the failing test, so it should read
the file first. Copying the teacher's next token may teach it to skip that read.

We can isolate this problem with a smaller task. An episode starts with a fresh
random bit. There are three possible action
tokens, `ANSWER_0`, `ANSWER_1`, and `INSPECT`. The teacher sees the bit and emits the
correct answer token. The student cannot see it, but can emit `INSPECT` to reveal
it at a cost of $$0.1$$. A correct answer earns one point. Returns are undiscounted.

The teacher always answers immediately. If the student fits those initial answers,
it learns to guess. Inspecting first would earn more reward, but the teacher never
needs to inspect.

Let the student inspect with probability $$q$$ and answer correctly afterward.
Otherwise, it guesses uniformly. Its expected return and initial imitation loss are

$$
J(q)=0.5+0.4q,
\qquad L_0(q)=\log 2-\log(1-q).
$$

| Inspection probability | Expected return | Initial imitation loss |
| ---------------------- | --------------- | ---------------------- |
| $$q=0$$                | $$0.5$$         | $$\log 2$$             |
| $$q=0.5$$              | $$0.7$$         | $$2\log 2$$            |
| $$q=1$$                | $$0.9$$         | $$\infty$$             |

The better policy has a worse initial imitation loss. Querying the same teacher
on more student rollouts does not change its initial answer.

This is a small example of the asymmetric imitation problem studied by adaptive
asymmetric DAgger, or A2D {% cite warrington2021a2d --file references %}. The expert's
extra information lets it choose actions that may be poor choices for its student.
We could adapt the teacher, ask it to act with the student's information, or use
reward to learn when inspection is worthwhile.

For the coding assistant, this means teaching it when to open the file as well as
how to write the patch afterward. More examples on student histories will not
supply that behavior if the teacher always answers from evidence the student lacks.

A teacher's greater knowledge can help the student learn from the same input.
The random bit isolates a different problem, since no amount of prior training
can reveal its value in a fresh episode.

## What should memory keep?

Now suppose the assistant does open the file. It reads the relevant code, runs a
few more commands, and compresses the conversation. If the summary drops that
code, the policy loses information it had already gathered.

Consider an agent that receives a fresh random code. Its next action must be the
single token `WAIT`. It then compresses its history. Later it is asked to
reproduce the code.

Keeping the code and forgetting it both allow perfect prediction of `WAIT`. That
step tells us nothing about whether the memory will support the later answer.

If the code has $$k$$ independent uniform bits, an agent that remembers nothing
can guess it with probability $$2^{-k}$$. If all its memory has at most $$2^b$$
possible states, its chance of reproducing the code is at most

$$
\Pr(\hat B=B)\le\min\{1,2^{b-k}\}.
$$

For integer $$0\le b\le k$$, keeping the first $$b$$ bits reaches this bound. For an
eight-bit code, keeping zero, four, or eight bits gives success rates of
$$1/256$$, $$1/16$$, and $$1$$. Any accessible cache, transcript, or note counts as
memory here. The bound concerns the number of possible memory states, rather than
a context length measured in tokens.

A summary can preserve the next action while losing information needed later.
For the coding assistant, the missing source code might not affect the next test
command. It can still be needed when the assistant writes the patch. Testing only
the next token would miss that loss.

I would evaluate a summary by whether the agent can still finish the task after
repeated memory updates, accounting for storage and retrieval costs. Continuous
Context Management already studies memory updates in language agents
{% cite hoy2026ccm --file references %}.

## Learning the policy

I started with a question about pretraining targets. Viewing the model as a
policy made the comparison precise enough to run, even though the results so
far are mixed and limited to predicting recorded actions.

For a coding assistant, I ultimately care whether it opens the right file and
writes a patch that works. A low imitation loss can coexist with skipping the
file read, copying an answer based on evidence it lacks, or forgetting the code
before writing the patch. I want to test behavioral language modeling against
those decisions as well.
